# 前后端验证一致性分析报告

## 一、发现的问题

### 1.1 必填字段有默认值（严重问题）

| 模型 | 字段 | 当前定义 | 问题 |
|------|------|----------|------|
| Inventory | unit | `Field(max_length=20, default="ml")` | ❌ 必填字段有默认值！ |
| InventoryCreate | unit | `Field(max_length=20, default="ml")` | ❌ 必填字段有默认值！ |
| ManualInventoryCreate | quantity_bottles | `Field(default=1, ge=1)` | ❌ 必填字段有默认值！ |

**影响**：这些字段即使前端不传值，后端也会保存默认值，可能导致数据不准确。

---

### 1.2 前后端验证不一致

#### 1.2.1 试剂订单 - unit 字段缺失

| 对比项 | 前端 ReagentOrderSchema | 后端 ReagentOrderCreate |
|--------|------------------------|------------------------|
| unit | ❌ 没有这个字段 | ✅ 必填 |
| 状态 | 无法提交 | 会报错 |

**问题**：前端没有 unit 字段，但后端要求必填。

#### 1.2.2 CAS号格式验证差异

| 对比项 | 前端 Valibot | 后端 validate_cas_format |
|--------|--------------|-------------------------|
| 正则 | `^\d{2,6}-\d{2}-\d$` | `^\d{2,7}-\d{2}-\d$` |
| 范围 | 2-6位 | 2-7位 |

**影响**：前端会拒绝 7 位 CAS 号（如 100027-00-5），后端会接受。

#### 1.2.3 规格验证差异

| 对比项 | 前端 SpecificationSchema | 后端 parse_specification |
|--------|-------------------------|------------------------|
| 正则 | `^\d+(\.\d+)?\s*(ml|l|g|kg|mg|个|瓶|支|盒|包|套)$` | `^(\d+\.?\d*)\s*([a-zA-Zμ个瓶支盒包套]+)$` |
| 接受 μL | ❌ 不接受 | ✅ 接受 ul/μl |

**影响**：
- 前端会拒绝 "500μL"，后端会接受并转为 "500mL"

#### 1.2.4 耗材订单 specification 必填性

| 对比项 | 前端 ConsumableOrderSchema | 后端 ConsumableOrderCreate |
|--------|---------------------------|---------------------------|
| specification | ❌ optional | ✅ 必填 (无默认值) |

**问题**：前端 Schema 定义为 optional，但后端要求必填。

---

### 1.3 formConfigs 必填标记不一致

在 `formConfigs.tsx` 中：

```typescript
// 试剂订单
{ name: 'specification', type: 'input', /* 没有 required: true */ }

// 耗材订单
{ name: 'specification', type: 'input', /* 没有 required: true */ }

// 库存 - 添加模式
{ name: 'specification', required: true }
```

**问题**：
- 试剂订单和耗材订单的 specification 在 formConfigs 中没有标记 required
- 但后端 ConsumableOrderCreate 要求必填

## 三、数据清洗情况

### 3.1 CAS号清洗

| 环节 | 清洗内容 | 实现 |
|------|----------|------|
| 前端 | 去除空格，转大写 | Valibot v.toUpperCase() + v.trim() |
| 后端 | 去除空格和制表符，转大写 | normalize_cas() |

**评估**：✅ 前后端都有清洗，不会储存错误格式的 CAS 号

### 3.2 规格清洗

| 环节 | 清洗内容 | 实现 |
|------|----------|------|
| 前端 | 无 | 只验证格式 |
| 后端 | 解析数值+单位，标准化单位 | parse_specification() |

**评估**：⚠️ 前端不清洗，后端清洗。但因为单位会被标准化，不影响最终存储。

### 3.3 拼音字段

| 环节 | 处理 | 实现 |
|------|------|------|
| 前端 | 无 | - |
| 后端 | 创建/更新时计算 | compute_pinyin_fields() |

**评估**：✅ 后端自动处理

## 四、修复建议

### 4.1 修复默认值问题

```python
# app/models/inventory.py

# 错误示例
unit: str = Field(max_length=20, default="ml")  # ❌

# 修复为
unit: str = Field(max_length=20)  # ✅ 无默认值

# ManualInventoryCreate
quantity_bottles: int = Field(ge=1)  # ✅ 移除 default=1
```

### 4.2 修复前后端不一致

1. **前端添加 unit 字段**到 ReagentOrderSchema
2. **前端 SpecificationSchema** 增加 μL 支持：
   ```typescript
   /^\d+(\.\d+)?\s*(ml|l|g|kg|mg|μl|ul|个|瓶|支|盒|包|套)$/i
   ```
3. **前端 CAS 正则** 放宽到 2-7 位：
   ```typescript
   /^\d{2,7}-\d{2}-\d$/
   ```
4. **ConsumableOrder specification** 在 formConfigs 标记 required: true

## 五、总结

| 检查项 | 状态 |
|--------|------|
| 必填字段有默认值 | ❌ 3处需要修复 |
| 前后端验证一致 | ⚠️ 多处不一致 |
| 数据清洗完整 | ✅ CAS号清洗到位 |
| 规格验证一致 | ⚠️ 格式略有差异 |

**建议优先级**：
1. **高优先级**：修复 unit 和 quantity_bottles 默认值（数据质量）
2. **中优先级**：统一 CAS 号和规格验证正则
3. **低优先级**：formConfigs 必填标记
