# 表单写入与超时结果核实

库存、订单、常用货架、CAS 主数据、品牌、公告、用户及设备的 JSON 写入，以及手工结构保存，共用操作凭据。CAS 识别、检索、登录、文件上传及会话续期沿用原有流程。

- 写请求携带 `Idempotency-Key`，格式为 12 位十六进制毫秒时间戳、下划线和 32 位随机十六进制字符。服务端按用户隔离，校验请求方法、路径、查询参数和 JSON 正文摘要。
- 操作号先占用；写入凭据与业务数据、必要业务日志使用同一个数据库事务提交。重复请求只返回原响应或“仍在确认”，不再次执行业务。
- 上述原子性针对数据库业务日志：源日志及其时间线投影一起提交或回滚，时间线以来源表和来源日志 ID 唯一约束防止重复投影。防重范围是同一用户的同一操作号；新操作号属于另一笔业务。`audit.log` 等异步文件日志不参与数据库事务，不能承诺与数据库同样的原子性及不丢失保证。
- 正常响应保存在凭据中。`GET /api/mutation-operations/{id}` 仅返回当前用户的操作结果，并禁止缓存；不保存请求正文，校验错误凭据移除输入原文。
- 一次前台提交的请求和结果查询共用 3 秒预算，到期即停止加载、保留弹窗和内容，并 toast 提示“获取提交结果超时，请刷新查看”。后台以本轮启动时刻为基准，在第 0、1、3 秒最多做三次只读结果查询，每次最多 1 秒，一轮最多约 4 秒；慢查询不会再额外累加间隔，不自动补发业务写入。同一用户、同一操作号的前后台查询共用在途请求，每个前台调用仍受自身的 3 秒预算约束。
- 后台查到结果会 toast 通知并保留原响应。用户用原内容再次点击提交时，在本次 3 秒预算内继续核实原操作；执行中或已提交但响应未完成时，每 250 毫秒查询一次。期间任一路径查到最终结果，当前提交直接恢复原响应，完成确认或后续步骤，不要求第三次点击，也不再次执行业务。前台正在核实时，后台仅缓存结果，不另发“再次点击”的通知。仍未查到结果才在本次预算用尽时提示超时；仅当状态接口明确返回 `missing`，且用户再次提交时，才在剩余预算内使用原操作号重新发送该操作。
- 等待截止通过独立错误对象传递，不在共享请求配置上保存“已超时”标记，避免一次状态查询超时影响同次提交的后续确认。后台任务每次发起查询前核对当前用户和操作号；原操作已确认并释放后，旧任务停止查询。
- 已成功写入后的列表刷新最多在前台等待 3 秒，超时继续后台刷新，不将尚未完成或被后续刷新替代的查询误报为失败；只有实际刷新失败才独立提示。3 秒提交超时不应用于列表读取。未知结果未确认前禁止换内容启动另一笔写入；后台核实不会自动关闭弹窗或覆盖用户输入，切换账号后停止旧账号的核实和通知。
- 操作号有效期为 7 天，服务端保留凭据时额外覆盖允许的 1 天设备时钟偏差，启动及运行中定期清理；过期操作号直接拒绝，不能因凭据被清理而重新执行业务。前端操作号随当前页面生命周期保存，刷新后表单仍按原约定清空。

`committed` 表示业务事务确实已经提交，但完整响应可能尚未产生。进程崩溃、提交后异常或凭据响应保存失败时，不伪造业务返回值，也不允许同一操作重新执行；这种结果仍需核实业务记录。多接口流程的凭据分别保证每一步，前端需保存已经成功的步骤；CAS 主数据补录后入架已接入步骤恢复。

新表 `mutation_operation` 由后端启动时的 `init_db()` 自动创建。此次变更不调整各业务接口的校验、权限和状态流转规则，也不更改 SSE 投递语义。

业务模块的 `APIRouter` 统一使用 `MutationTrackedRoute`，通过 `dependencies` 和 `get_route_handler` 扩展点接入凭据。不得通过遍历 `app.routes` 修改已生成的依赖树接入：FastAPI 的延迟 `include_router` 不会使用这份依赖树，导致状态查询存在而实际写入没有防重保护。新增模块必须覆盖 `include_router` 及真实 HTTP 超时重试测试。
